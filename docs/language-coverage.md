# What the Checker Catches Today

> **Status page:** which kinds of TypeScript programs tsox checks correctly, which it stays quiet about, and where it is wrong, measured against `tsc` and not claimed.

This page says what works. It is measured, so it can be refreshed and checked: each row below is a small program run through both `tsc` 6.0.3 and tsox, and the results are generated by [`scripts/coverage-probes.py`](../scripts/coverage-probes.py). For how tsox does on real compiler tests, see the [conformance baseline](conformance/baseline-part01-05.md); the two answer different questions (section 5).

## 1. How it is measured

A **probe** is a project of one to three files with one deliberate fault, checked with `strict` on (target `es2022`, `moduleResolution: bundler`). `tsc` is the reference. The result is one of:

| Result | Meaning |
| --- | --- |
| **MATCH** | tsox reports the same error codes in the same files as `tsc` (including none, for a valid program) |
| **GAP** | tsox reports some of what `tsc` does, usually nothing, and often a warning that a construct is not checked yet |
| **DIFF** | both report errors, and the codes differ |
| **FALSE-POS** | tsox reports an error `tsc` does not. This is the result that matters most |

There are 98 probes in ten areas: nine of faulty programs and one of valid programs. Twenty of them are *valid* programs, with no error in `tsc`, so that any tsox error on them shows up as a false positive and not as a quiet gap. Measured on 2026-11-04 with tsox at `e734416` and `tsc` 6.0.3.

## 3. What the results say

**Checked, and the same as `tsc`.** Primitive and object assignability, `null` and `undefined` under strict checks, calls and argument counts, excess and missing properties, interfaces and `extends`, unions with every narrowing form tried (`typeof`, `in`, `instanceof`, discriminants, type predicates and assertion functions; three of these report TS2339 where `tsc` reports its spelling-suggestion variant, see below), generic inference and constraints, overload resolution, class members, inheritance, property initialization, parameter properties and accessors, enums, tuples, `keyof`, indexed access, conditional types with `infer`, `Partial` and `Pick`, and `async` and `await`. Across files, an import of every declaration kind tried (functions, interfaces, classes, enums, type aliases, generic and overloaded functions, default exports, namespaces, `const enum`, inferred exports and re-exports) is checked as `tsc` does, including a missing export, a missing module and a circular import.

**Not checked: the check is not written yet.** tsox stays silent. These are rules that need no new type machinery and are not enforced yet:

| Rule | `tsc` code |
| --- | --- |
| A variable used before it is assigned | TS2454 |
| Assigning to a `readonly` property, and mutating an `as const` array | TS2540, TS2339 |
| Instantiating an abstract class | TS2511 |
| Reading a `private` or `#private` member from outside | TS2341, TS18013 |
| A class that does not implement its interface, or overrides a member with an incompatible type | TS2420, TS2416 |
| `for ... of` over a value that is not iterable, and a generator that yields the wrong type | TS2488, TS2322 |
| A member that does not exist on a namespace | TS2339 |
| `satisfies` | TS2322 |
| An optional property used where the type does not allow `undefined` | TS2322 |

**Not checked: the type cannot be resolved yet.** A mapped type, a template literal type and an index signature leave the annotation unresolved. tsox says so with a warning (`TSR9012`, "Type annotation ... could not be resolved") and does not guess. The `Record` utility type is not resolved and gives no warning.

**Typed loosely on purpose.** `array.map(f)` and `promise.then(f)` accept a callback and return `any`, so an error in how their result is used is missed and none is invented. See [library-and-ambient-declarations](architecture/library-and-ambient-declarations.md).

**Different code.** Five probes report an error in the right place with another code. Three are the same error where `tsc` found a similarly spelled property and reports TS2551 ("Did you mean ...?") in place of TS2339. One is a call whose object literal has an extra property, which `tsc` reports as TS2353 (an excess property) and tsox as TS2345 (an argument that does not match). One is the static member below.

**Wrong: static members.** Valid code that reads a static member through the class name, `A.s` or `A.make()`, gets a false `TS2339` from tsox (`Property 's' does not exist on type '() => A'`), in one file and across files. The class value is typed as its constructor and its static members are not on it. This is the only false positive in the probes: the other 17 valid programs are clean. It is a defect to fix, and until then a project that uses static members will see false errors. The bodies of static methods are checked; it is the access through the class name that is not resolved.

**Warnings are the checker saying "not yet".** `TSR9006` is an expression kind not checked yet, `TSR9008` a class whose shape is not checked yet, and `TSR9012` an annotation that cannot be resolved. A gap that warns is the checker working as designed: it costs completeness and never correctness (see [partial-results](architecture/partial-results.md)).

## 4. What the probes do not cover

Probes test the surface of the language, one fault at a time. They do not measure how tsox behaves on large real programs, on libraries with deep generic types, or on anything that needs the full standard library, which the checker does not have yet. They do not test performance. Decorators, `unique symbol`, declaration merging beyond interfaces, JSX and the `lib` option are not probed.

## 5. Probes and the conformance corpus

The [conformance baseline](conformance/baseline-part01-05.md) runs 2,499 files of the TypeScript compiler's own test corpus and finds about half matching, about two in five gaps and a few percent false positives. The probes show a higher match rate for a reason worth stating: a probe is one fault in a small program, chosen to test a feature the checker is meant to cover, and a corpus file is a real test written to exercise an edge of the compiler. The probes say which features work. The corpus says how far that goes on real code. Neither number is a substitute for the other.

## 6. Refreshing this page

```text
cargo build --release
(cd scripts/ts-diag-tool && npm ci)
python3 scripts/coverage-probes.py                 # a summary and every non-match
python3 scripts/coverage-probes.py --markdown      # the tables below
```

When a gap is closed, the probe that showed it turns to MATCH; add a probe for any new feature, and add a valid-program probe for anything that could produce a false error.
